# احتياجات ربط شاشة فاتورة المشتريات

الشاشة الحالية نموذج Frontend محلي يفتح من الموردين. لا تستدعي API ولا تعدّل أرصدة الموردين أو المخزون الفعلي. تخزن بيانات التجربة في `ghaith-purchase-prototype-v1` عبر `src/core/purchase-storage.js`، والمعرفات التجريبية لا تُرسل للخادم كما هي.

## البيانات التي تستخدمها الشاشة

- المورد: معرف، اسم، هاتف، عنوان. إنشاء مورد أثناء الفاتورة يختاره تلقائيًا.
- التصنيف: معرف واسم فريد. إنشاؤه أثناء إضافة المنتج لا يفقد بيانات النموذج.
- نسخة المنتج: معرف، اسم المنتج، التصنيف، اللون، المقاس، باركود، SKU، سعر الشراء، سعر البيع، المخزون، حد إعادة الطلب.
- الفاتورة: معرف، معرف المورد، رقم فاتورة يولّده الخادم، تاريخ الفاتورة، تاريخ الاستحقاق، الملاحظات.
- البنود: معرف النسخة، كمية صحيحة موجبة، سعر الشراء، خصم السطر كقيمة نقدية.
- الحسابات: خصم إضافي نقدي، مصاريف شحن، إجمالي نهائي.
- السداد: كامل أو جزئي أو آجل، المدفوع، نقدي/تحويل بنكي/محفظة/بطاقة، المرجع.

## قواعد الحساب الحالية

1. مجموع البنود قبل الخصم = مجموع (الكمية × سعر الشراء).
2. الإجمالي = مجموع البنود − خصومات السطور − الخصم الإضافي + الشحن. لا توجد ضريبة في الفواتير الجديدة.
5. المتبقي = الإجمالي − المدفوع. الكامل يسدد الإجمالي، والآجل مدفوعه صفر.
6. الدفع الجزئي يشترط مبلغًا موجبًا أقل من الإجمالي. الاستحقاق مطلوب عند وجود سداد جزئي أو آجل ولا يسبق تاريخ الفاتورة.
7. تكرار مسح نفس النسخة يزيد كمية السطر. خصم السطر قيمة إجمالية ثابتة، لا خصم لكل قطعة.

## المطلوب من الباك إند عند الربط

- الحفاظ على endpoints الحالية، وإضافة الدعم الناقص بالاتفاق مع الفريق.
- إدارة Product/Variant بالألوان والمقاسات، وضمان تفرد الباركود وSKU على مستوى قاعدة البيانات.
- بحث المنتجات والنسخ بالباركود والاسم وSKU، مع قائمة موردين وتصنيفات قابلة للبحث والترقيم من الخادم.
- حفظ وقراءة وتعديل المسودات دون ترحيل للمخزون أو حساب المورد.
- اعتماد ذري للفاتورة: إعادة حساب الإجماليات، التحقق من الصلاحيات والكميات والمدفوع، ترحيل المخزون وحساب المورد والدفعة الأولى وحركة المخزون في عملية واحدة.
- منع الاعتماد المتكرر باستخدام idempotency والتحقق من النسخة الحالية للبيانات؛ لا تعتمد على تعطيل زر الواجهة وحده.
- حفظ حقول التاريخ والخصومات والشحن والمرجع وطريقة الدفع.
- توليد رقم الفاتورة تلقائيًا في الخادم وإرجاعه مع الفاتورة. لا تقبل الواجهة رقمًا يدويًا. أرقام LOCAL الحالية مراجع تجريبية لا تُرسل كأرقام رسمية.
- إرجاع تفاصيل الفاتورة المعتمدة وإجماليات موثوقة ورقم داخلي يصلح للطباعة، مع أخطاء validation مرتبطة بالحقول.
- إضافة سجل دفعات الموردين والسداد اللاحق في المرحلة التالية؛ ليس ضمن شاشة الإنشاء الحالية.

## حدود النموذج المحلي

- مسودة واحدة محفوظة على المتصفح، وسجل فواتير معتمدة محليًا للعرض والطباعة.
- إغلاق الشاشة أو إعادة تحميلها يحاول حفظ التعديلات كمسودة.
- بيانات المنتجات والموردين الجديدة محلية لهذه التجربة ولا تظهر تلقائيًا في صفحات الإدارة المتصلة بالخادم.
- الاعتماد المحلي لا يرحّل أي مخزون أو مديونية. عند الربط، يستبدل service المحلي باستدعاءات الخادم ونتائجه دون اختراع endpoints.

## تحقق الواجهة

`tests/purchase-invoice.test.cjs` يختبر المسح المتكرر، إنشاء تصنيف ومنتج داخل الفاتورة، سيناريو 20000/8000/12000، منع زيادة المدفوع، استعادة المسودة، حفظ الفاتورة، إنشاء المورد، العرض المتجاوب والطباعة. يستخدم متصفح اختبار مستقل وبيانات جلسة وهمية ولا ينفذ عمليات على الخادم الحقيقي.

## طباعة 80 مم

زر الطباعة يفتح حوار طباعة المتصفح بإيصال عرضه 80 مم، مع طول محسوب من المحتوى. اختر الطابعة الحرارية وورق 80 مم ومقياس 100%. جدول الطباعة يعرض الصنف والكمية والسعر والإجمالي، وتظهر تفاصيل النسخة أسفل الاسم. لم يتم تغيير خدمة الطباعة المحلية أو اختبار إخراج ورقي فعلي. الفواتير المعتمدة القديمة تحتفظ بإجمالياتها، وأي ضريبة سابقة تظهر كبند تاريخي؛ المسودات المستكملة والفواتير الجديدة تُحسب بدون ضريبة.
